> **TL;DR**: 「資料會不會外流」是企業主管評估 AI agent 時最常問的問題，但它只是三層風險裡的第一層，也通常是最好處理的一層。真正容易出事的是第三層：agent 碰得到什麼、能做什麼。這層要靠權限設計管，不能靠 prompt 提醒它「要小心」。

## 主管最常問的，是第一層

跟企業主管談 AI 導入，第一個問題幾乎都是：「我們的資料會不會外流？」

這題很合理，我也不覺得是問錯。但如果整個評估只停在這題，就會漏掉更容易發生的事。

我會把 AI agent 的資安拆成三層，每一層要管的東西不一樣，該問的問題也不一樣。

## 第一層：資料會不會被拿去訓練、會不會外流

這層最常被問，但通常也最好處理。主流廠商的企業方案多半在合約裡寫明了不拿客戶資料訓練、資料存放在哪、留存多久。去讀條款，確認這幾件事，這層大致就收斂了。

真正讓這層出事的，往往不是廠商，而是員工在公司沒提供工具的情況下，自己拿個人帳號處理公事。這是另一個題目，我之後另外寫。

## 第二層：它會不會講錯話

客服 agent 回錯退款政策、亂承諾交期，這種事比資料外流更容易每天發生。

要管的有兩件事。第一，它的回答被限制在哪些文件裡：只能從核准過的 SOP、政策、FAQ 裡找答案，找不到就說不知道或轉給人。第二，上線前有沒有用真實問題測過一輪，之後改了設定、換了文件，有沒有用同一批問題重測。

第二層的風險是「說錯」，傷的是信任和客訴量。它很煩，但還在對話裡。

## 第三層：它碰得到什麼、能做什麼

這層最少人問，因為大家心裡的畫面還是「一個會回話的 chatbot」。

但一個客服 bot 只要能回答「我的訂單到哪了」，它就已經在查訂單系統、讀客戶資料了。它不只是在講話，它在存取資料。下一步讓它退款、改地址、寄通知信，它就開始動手了。

這時候真正的外流路徑，往往不是模型廠商拿你的資料去訓練，而是 A 客人問了一句話，bot 查出了 B 客人的訂單。

### 一個真實案例

今年 4 月，資安公司 Capsule Security 揭露了 Microsoft Copilot Studio 和 Salesforce Agentforce 的兩個漏洞（[CSO Online 報導](https://www.csoonline.com/article/4159079/copilot-and-agentforce-fall-to-form-based-prompt-injection-tricks.html)）。

攻擊方式很樸素。在 Copilot Studio 的案例裡，攻擊者把一段指令藏在 SharePoint 表單的一般欄位裡，像是備註欄。Agent 處理這筆表單時，把那段文字當成指令執行，把串接的 SharePoint 清單裡的客戶姓名、地址、電話寄給了外部。Agentforce 的案例類似：公開的潛在客戶表單裡藏了指令，內部同事請 agent 處理這筆 lead 時，指令被執行，CRM 資料被撈出來寄出去。

Microsoft 修了，給了 CVE 編號。Salesforce 的回應很值得讀：他們說這個外流是「configuration-specific」，跟可選的 human-in-the-loop 設定有關。

這兩家都是最大的廠商，模型也都是頂尖的。資料沒有被拿去訓練，第一層完全沒出事。出事的是第三層：agent 能讀客戶資料，又能自己寄信出去，中間沒有任何一道關卡。

所以如果有老闆看到這種新聞問我「AI 是不是不安全」，我的答案是：這是權限沒設計好。

## 第三層要怎麼管

我在 Codeer 做的就是讓企業把 AI agent 放到客戶面前的平台，所以這層是我們每天在處理的事。講兩個我們實際的做法。

### 身分由系統注入，不讓 agent 自己填

假設查訂單需要客人的 email。最直覺的做法，是讓 agent 從對話裡判斷這個人是誰，再把 email 帶進查詢。

我們不這樣做。設定 tool 的時候，email 欄位是一個類似 `{{user.email}}` 的變數，在 tool use 這一層由系統把登入者的身分注入進去。Agent 根本沒有機會決定要查誰的訂單，所以它不會弄錯，也沒辦法被騙去造假。

這就是「限制要做在系統權限裡」的意思。你可以在 prompt 裡寫一百遍「只能查這位客人自己的訂單」，但 prompt 是請求，不是限制。上面那個案例已經示範過：只要 agent 讀到的內容裡藏了指令，它就可能照做。

### 用「錯了能不能撤回」決定要不要人工核准

第二個是核准。哪些 tool 可以讓 agent 直接執行，哪些送出前要等人按確認？

我們用 two-way door 和 one-way door 來分。查訂單、查庫存、回答政策問題，弄錯了大不了再查一次，這種可以讓 agent 直接做。退款、刪資料、對外寄信，做了就收不回來，這種送出前要有人核准。

這件事沒有通用答案，每個 tool 都要拿出來討論：這個動作錯了會怎樣？誰會受影響？撤得回來嗎？哪些 case 底下其實弄錯無所謂，哪些 case 絕對不能錯，要好好討論過，而不是上線前一口氣全開或全關。

全部都要核准，agent 就沒用了，客人等不到回覆。全部都不核准，就會像上面那個案例一樣，少了這道關卡。

## 別倒向另一邊

講到這裡，很容易得出「那 AI agent 還是先別碰比較安全」的結論。

這個結論一樣太快。第三層的風險，本質上跟你開一個系統帳號給新進工讀生是同一類問題：他能看到什麼、能做什麼、什麼事要主管簽核。企業早就知道怎麼管人的權限，只是還沒意識到 agent 也需要一樣的設計。

反過來，也別因為廠商合約寫得很漂亮，就覺得資安這題已經過關。第一層過了，只代表第一層過了。

## 評估 AI agent 時，多問這四題

不管你選哪家、還是自己做，下次評估時，除了問資料會不會外流，再多問四個問題：

1. 它查資料時用的是誰的身分？這個身分是系統給的，還是 agent 自己判斷的？能看到的範圍有多大？
2. 它的回答，能不能只來自我們核准過的文件？
3. 改了設定之後，有沒有辦法用同一批真實問題重測一次？
4. 哪些動作會在送出前停下來等人核准？這份清單是誰決定的？

這四題都答得出來，才算真的把風險管住。
