> **TL;DR**: 傳統公司的流程，是在沒有 AI 的前提下長出來的。把 AI 加進去，分工、審查、權限都照舊，多半只是多燒 token。重新設計一個流程，要改的是三件事：哪些判斷從人移到檢查機制、agent 看得到什麼、agent 能動什麼。我們在 Codeer 先重畫的是軟體開發流程：behavior 測試過、AI review 過的 code 就可以 merge，agent 可以看 production log 和有限制的 production db。整間公司一次重來不現實，挑一個流程開始就夠了。

## 加上去和重畫，差在哪

我之前在〈[你喊的 10x，是 activity、output，還是 outcome？](/posts/ai-10x-productivity-activity-output-outcome/)〉用過工廠電氣化的例子：只把蒸汽機換成電動馬達，產線佈局照舊，生產力幾乎沒動。要等到廠房照著電力重畫佈局，提升才出來。

AI 導入也是一樣的結構。我前幾天在 LinkedIn 寫過一個看法：傳統公司本來就不是為 AI 設計的。組織怎麼分、流程怎麼走、誰負責判斷，全都是在沒有 AI 的前提下長出來的。

所以先把兩件事分開：

- **加上去**：分工、審查、權限照舊，只把其中幾個步驟換成 AI。工程師用 AI 寫 code，但每一行還是照原本的方式 review；客服用 AI 草擬回覆，但還是每一則都人工確認。
- **重畫**：假設 agent 會參與整件事，重新決定每一步誰做、誰判斷、需要看到什麼。

加上去的版本，產出變多，判斷的成本沒變，瓶頸只是搬到 review 那一關。重畫的版本，要動的是信任和權限，所以比較難，也比較少人做。

整間公司一次重畫不現實。我們自己也只先重畫了一個流程。

## 我們先重畫的流程：軟體開發

我得先交代立場：Codeer 是六個人的團隊，做的是 AI agent 平台。我們重畫流程的成本，比一間幾百人的企業低很多。但正因為小，改了什麼、效果如何，看得比較清楚。

我們最主要重畫的是軟體開發流程。原因很直接：agent 寫 code 和 debug 的能力越來越強，如果流程還是照「人寫、人逐行審、只有人能碰 production」的方式走，agent 的能力就卡在流程上。

我們放出去的權限，大概分三層：

**第一層：寫和 merge。** 我們對 agent 寫的 code 更加信任。behavior 測試過、經過 AI review，就可以 merge。人不再逐行看每一個 PR，人看的是 behavior 有沒有被測到、風險高的改動有沒有被挑出來。這件事的細節，我在〈[AI Coding Workflow 裡，人類該 Review Plan 還是 Evidence？](/posts/what-humans-review-ai-coding-workflow/)〉寫過。

**第二層：看得到 production。** agent 可以看 production log。debug 最花時間的部分是找 context，翻 log、對 code、串起事情發生的順序。這段交給 agent，人拿到的是一份已經串好的推論，判斷它對不對就好。這跟我在〈[我砍過一個 AIOps 產品，五年後 AI 五分鐘就做到之前做不到的事](/posts/aiops-root-cause-in-five-minutes/)〉寫的是同一件事。

**第三層：有限制地碰資料。** agent 可以存取有限制的 production db。這層最敏感，所以「有限制」是重點：看得到什麼、能做什麼，都是事先設計好的。這是我在〈[資料會不會外流，只是 AI 資安的第一層](/posts/data-leak-is-only-layer-one/)〉講的第三層：agent 碰得到什麼、能做什麼，比模型本身更值得花時間設計。

三層放在一起看，重畫流程改的是兩件事：

1. **哪些判斷從人移到檢查機制。** 以前「這段 code 能不能 merge」是人逐行判斷，現在大部分交給 behavior 測試和 AI review，人只處理風險高的部分。
2. **agent 看得到什麼、能動什麼。** 一個看不到 log 的 agent，只能做被切好的小任務。看得到 log、有限制地碰得到資料，它才能把一件事從頭做完。

## 組織會跟著變

流程重畫之後，組織也會被推著變。如果現在要從頭開一間公司，有三件事我會一開始就這樣設計：

**招募能 e2e 完成工作的人。** 以工程師為例，要能做產品規劃、前端、後端，也能面對客戶。agent 把很多中間步驟做掉之後，最貴的是交接。一件事在三個人之間傳，每傳一次就掉一次 context。

**所有 infrastructure 和 software 都預設 agent 會 access。** 選工具、設權限、寫文件時，先問 agent 用不用得到。只有人看得懂的東西，agent 就幫不上忙。

**為 agent 做工具。** 給人用的介面，agent 用起來常常很笨拙。我們會花時間做專門給 agent 用的工具，讓它拿資料、跑檢查、回報結果都有固定的路可以走。

這三件事，傳統公司不一定能馬上做到。但它們指出重畫的方向：減少交接、讓 agent 看得到、讓 agent 有路走。

## 主管最常問的兩個問題

跟企業客戶談的時候，重畫流程最常卡在兩個問題。

### 資料還沒準備好，要先整理嗎？

很多主管覺得要先把資料整理好，才能開始做 AI。

鄧白氏第四季的台灣企業 AI 動能指數（[MoneyDJ 報導](https://tw.stock.yahoo.com/news/q4%E5%8F%B0%E4%BC%81ai%E5%8B%95%E8%83%BD%E7%BA%8C%E6%93%B4%E5%BC%B5-78-%E4%BC%81%E6%A5%AD%E5%B7%B2%E8%B7%A8%E8%B6%8A%E8%A6%8F%E5%8A%83%E6%88%96%E8%A9%A6%E8%A1%8C%E9%9A%8E%E6%AE%B5-025600226.html)）顯示，台灣只有約 9% 的企業資料完全準備就緒。資料完全就緒的企業裡，77% 說已取得廣泛或顯著的 AI 回報；部分就緒的只有 13%。

這組數字常被讀成「先把資料準備好」。但它講的是相關，沒有告訴你順序。資料完全就緒的公司，可能本來就是組織比較成熟的公司。

我們的做法是兩件事同時做：先很快做一版讓客戶體驗，同時跟客戶一起準備資料。原因是資料缺在哪裡，通常要等有一版能用才看得出來。先整理一年資料再開始，很可能整理到的是用不到的部分。

### AI 答錯怎麼辦？

主管的擔心，很多是想像出來的：「AI 公司會不會把我的機密拿走？」「AI 回答錯了怎麼辦？」這些擔心不是沒道理，但要拿來跟現況比。

我通常用三種方式回答：

1. **先 scope 一個風險相對小的範圍。** 第一個流程不要挑錯了就出大事的。
2. **一起訂好內部測試流程。** 上線前用真實的問題測，改動之後重跑。
3. **拿現況分析擔憂合不合理。** 例如有人擔心 AI 客服會答錯。但如果客服原本是由比較資淺的人擔任，本來也可能答錯。差別是資淺同事答錯，通常沒人知道；AI 客服答錯，每一次都有紀錄，可以找出來、可以 optimize。

第三點最常讓主管改變想法。他們拿來比較的，常常是一個不會出錯的理想狀態。現況從來沒有那麼好。

## 別倒向另一邊

講到這裡，很容易得出「所以就該大膽放權」的結論。這也太快。

我們放出去的權限，每一層都有前提。merge 的前提是 behavior 測試和 AI review；看 production 的範圍是 log；碰資料的前提是有限制。高風險的改動，人還是會看。我在〈[「這是 AI 生的」不是品質差的理由](/posts/same-bar-for-ai-output/)〉寫過：錯了的代價有多大，決定需要多少人的判斷。

反過來，也別因為一間公司重畫不了全部，就覺得 AI 導入沒有意義。挑一個流程重畫，做出來之後，下一個流程就有樣子可以照著改。

## 挑一個流程重畫之前，先問四題

1. 這個流程裡，哪些判斷現在是人在做，可以改成檢查機制？
2. agent 需要看到什麼，才能把整件事從頭做完，而不是只做被切好的一小段？
3. 哪些權限只給看，哪些要有限制，哪些暫時不給？
4. 出錯的時候，有沒有紀錄可以追、可以改？

四題都答得出來，這個流程就可以開始重畫。答不出來的那一題，就是第一個要補的地方。
